binaryang IR Map

One tree, two verb sets. The reader and the encoder are shared; the fidelity operations and the optimizer passes are separate sets of functions over the same Module. Fidelity data lives beside the tree, keyed by node id, and the optimizer drops it.

Var ├─ customSections Custom[] ← binaryang.text-form (v2) travels here ├─ sectionMeta SectionMeta[] { section, offset, size, count } as read ├─ fidelity FidelityTable NodeId → as-written entry; dropped by the optimizer ├─ hasNameSection, explicitNames? └─ optimizeStack?
Why nodeId, not object identityThe text-path passes rebuild nodes by spread (about 100 sites). A spread copies the id, so the side table survives; a newly constructed node gets no id and falls back to derived values.
Two names for one typeType is core's value-type enum. A node's type field is ExprType. Expression, WasmModule, WasmFunction are the same records under binaryen-ts's names.
Regions everywhereFunction bodies, if-arms, global and table initialisers, and element offsets are all RegionExpr, so one walker covers code and constant expressions.
